# AGENT.md — LeadFlow Engineering Rules

These rules apply to every change in this repository, by humans and AI agents alike. If a rule and a shortcut conflict, follow the rule.

## 1. Project overview

LeadFlow is a single-screen lead management tool: a lead list (status badges, last note, time since last discussion, status filter, name search, today's follow-ups pinned, overdue follow-ups in red), a lead timeline dialog (discussion history newest-first, add note with optional follow-up, change status), and an add-lead dialog.

### Stack

| Layer | Choice |
|---|---|
| Frontend | Next.js latest (App Router), TypeScript strict, Tailwind CSS |
| Server state | TanStack Query |
| Dialogs | Radix Dialog |
| Forms | react-hook-form + zod |
| Backend | FastAPI, Pydantic v2, Python 3.12 |
| DB | SQLAlchemy 2.0 + Alembic. SQLite locally; Neon Postgres in production (psycopg 3). Keep SQL portable so both work, and run the API tests against Postgres via `TEST_DATABASE_URL` when touching models or queries |
| Hosting | Vercel: `backend/` (FastAPI) and `frontend/` (Next.js) as two projects |
| Tests | pytest + httpx (API); Vitest + Testing Library (UI) |
| Lint/format/types | ruff + mypy --strict (API); ESLint + Prettier + `tsc --noEmit` (web) |
| Delivery | Docker Compose (web + api), `.env.example`, seed script |

### Layout

```
leadflow/
  AGENT.md  README.md  docker-compose.yml  .env.example  Makefile
  backend/app/
    main.py          app factory, CORS, router mounting, exception handlers
    core/            config.py, db.py, errors.py
    models/          SQLAlchemy models (Lead, Discussion)
    schemas/         Pydantic request/response models
    repositories/    DB access only
    services/        business rules
    api/routes/      thin routers
    seed.py          >= 5 leads with discussions
    tests/
  frontend/src/
    app/             layout.tsx, page.tsx (single screen)
    components/      one component per file; ui/ holds shared primitives
    hooks/           TanStack Query hooks
    lib/             api client, types, time/follow-up helpers, constants
```

The browser calls `/api/v1/...` on the Next.js origin; `next.config.ts` rewrites `/api/*` to `API_INTERNAL_URL`. "Today" is computed in the browser (local timezone), so the API does not group leads. `frontend/AGENTS.md` is generated by Next.js; keep it.

Run `npm run check` in `frontend/` and `ruff`, `mypy`, `pytest` in `backend/` (see `make check`).

## 2. Workflow and git

- Branch off `main`. Small, focused commits: one concern each.
- Conventional Commits: `feat(api): add discussion endpoint`, `fix(web): ...`, `test:`, `docs:`, `chore:`, `refactor:`.
- Never commit with failing lint, type check or tests.
- Never commit secrets, `.env`, database files, `node_modules`, `.venv`.
- README must disclose how AI was used.

## 3. General rules

- No dead code, no commented-out code, no `TODO` without a tracked issue.
- No magic strings or numbers: use enums and named constants (lead statuses defined once per side and mirrored).
- Functions <= 40 lines, files <= 250 lines. Split before exceeding.
- Prefer early returns over nesting. Explicit over clever.
- Names describe intent; no abbreviations except common ones (`id`, `url`).
- Configuration only via environment variables read in `core/config.py` (backend) or `process.env` in one module (frontend).
- Do not add dependencies without a stated reason in the commit message.
- Avoid useless comments. Never restate what the code does, narrate steps, or add section banners; fix unclear code with better names instead. Add a comment only for a non-obvious *why* (hidden constraint, workaround, surprising behaviour). No docstrings that merely repeat the signature.

## 4. Backend rules

- Layering is strict: route -> service -> repository -> model. Routes never touch the session; repositories contain no business rules.
- Full type hints everywhere; `mypy --strict` and `ruff` must pass.
- Every request and response uses a Pydantic schema. Never return ORM objects.
- Use `Depends` for DB session and services. No global mutable state.
- All datetimes are timezone-aware UTC. Convert only at the edge.
- Status codes: 200 read/update, 201 create (with `Location`), 204 no body, 404 missing resource, 409 conflict, 422 validation, 500 unexpected. Never return 200 with an error body.
- Domain exceptions (`NotFoundError`, `ConflictError`, ...) are raised in services and mapped to HTTP in one place. Error envelope: `{"error": {"code": str, "message": str, "details": any?}}`. Never leak stack traces.
- Saving a discussion with `follow_up_at` updates `Lead.follow_up_at` in the same transaction.
- Schema changes go through Alembic migrations, never ad-hoc `create_all` outside tests.
- Endpoints (under `/api/v1`): `GET /leads?status=&q=`, `POST /leads`, `GET /leads/{id}`, `PATCH /leads/{id}/status`, `POST /leads/{id}/discussions`. Do not invent others without updating this file.
- Every endpoint has pytest coverage for the happy path and each error path.

## 5. Frontend rules

- TypeScript `strict`. No `any`. No `as` casts without a comment justifying them.
- Function components only; one component per file; PascalCase components, camelCase hooks prefixed `use`.
- Server Components by default; add `"use client"` only for interactive components.
- Presentational components take props and do not fetch. Components never call `fetch` directly: component -> hook -> `lib/api` client.
- All server state through TanStack Query hooks. Mutations invalidate the leads query so the list updates immediately; status change may update optimistically and must roll back on error.
- API types live in `lib/types.ts` and mirror backend schemas.
- Styling with Tailwind utility classes and design tokens only; no inline styles.
- Every async view handles loading, empty and error states.
- Accessibility: labelled inputs, Radix focus trap, Escape closes dialogs, status not conveyed by colour alone, visible focus rings.
- Overdue follow-ups render red; today's follow-ups render in the pinned section; Won/Lost are visually de-emphasised.
- Search input is debounced; filters and search are reflected in query params sent to the API.

## 6. Testing

- Backend: services (follow-up sync, status change), every route, validation errors, 404s.
- Frontend: time-ago and follow-up helpers, add-lead form validation, note form (follow-up date+time), status filter behaviour.
- `make check` runs lint, type check and tests for both sides and must pass before every commit.
- Tests use an in-memory SQLite database and never touch the dev database.

## 7. Docs and delivery

- README includes: overview, Docker Compose quick start, manual setup (backend + frontend), seed command, env var table, API table, AI-usage disclosure.
- Keep `.env.example` and OpenAPI docs in sync with the code.
- Seed script must be idempotent and create at least 5 leads with multiple discussions, including a follow-up today and an overdue one.

## 8. Definition of done

- [ ] Lint, types and tests pass (`make check`)
- [ ] New behaviour has tests
- [ ] No unrelated changes in the diff
- [ ] README / `.env.example` updated if setup or API changed
- [ ] Conventional Commit message, one concern per commit

## 9. Rules for AI agents

- Read the surrounding code and this file before editing; match existing style.
- Make only the requested change; no drive-by refactors.
- Do not add endpoints, dependencies or files outside this structure without saying why.
- Run `make check` (or the relevant subset) and report exactly what ran and its result; never claim success without running it.
- Ask when requirements are ambiguous instead of guessing.
